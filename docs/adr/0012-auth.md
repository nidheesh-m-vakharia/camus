# ADR 0012: Authentication and dev mode

Status: Proposed
Date: 2026-11-05

## Context

Kafka clients will not connect unless the security protocol matches the
broker. Production traffic should not be anonymous on a network. The first
milestone still has to be runnable on a laptop without certificates.

## Decision

Two listener modes.

### `PLAINTEXT`, opt-in

A listener binds as Kafka `PLAINTEXT` only when config sets
`listener.dev_plaintext=true`. The default is false. If the bind address is
not loopback, startup also requires `listener.allow_non_loopback=true`.
Missing either flag is a startup error, not a warning.

This mode performs no SASL and no TLS. It exists for docker-compose, the
client compatibility suite, and local demos. `docs/compatibility.md` lists
it as a supported dev configuration, not as the production default.

Phase 0 and Phase 1 bring-up uses this mode so protocol tests are not
blocked on TLS.

### `SASL_SSL` with SASL/PLAIN

The production listener is TLS plus SASL/PLAIN.

- TLS terminates in the broker with `tokio-rustls`. Certificate and private
  key come from files. mTLS is out of scope.
- SASL/PLAIN checks username and password against a config file loaded at
  startup, or against an environment variable for single-user deploys.
  Passwords are not logged. Comparison is constant-time.
- The Kafka handshake order is preserved: `ApiVersions` may be the first
  request, then `SaslHandshake` and `SaslAuthenticate`, then other APIs.
  Any other API before a successful authentication gets a TCP close or
  `ILLEGAL_SASL_STATE` (34), following the 4.4.0 broker once that path is
  read. Until the code is checked against `KafkaApis`, Phase 1 implements
  the sequence the Java client actually sends and records the trace in the
  PR.
- SCRAM, OAUTHBEARER, GSSAPI, and delegation tokens are not implemented.
  They are absent from `ApiVersions` / SASL mechanism lists. A client that
  requests them gets the Kafka error for an unsupported mechanism, not a
  successful anonymous session.

ACLs are Phase 5. Until then, an authenticated (or dev-plaintext) client
may access every topic. There is no pretend authorizer that allows
everything while returning success from `DescribeAcls`. Describe ACLs
returns `UNSUPPORTED_VERSION` until Phase 5.

## Consequences

- The compatibility docker-compose file sets the two dev flags and never
  ships as a production compose file without a comment at the top that says
  so.
- Phase 1's "SASL/PLAIN + TLS" acceptance test can land at the end of the
  phase, after PLAINTEXT produce/fetch is green. The phase is not done
  until that test is green or the review explicitly cuts it. The brief
  includes it in Phase 1, so the default is to include it.

## Alternatives

- PLAINTEXT as the default. Rejected. A default that is safe on localhost
  and unsafe everywhere else gets copied into production.
- SASL/PLAIN without TLS. Rejected for the production listener. PLAIN sends
  the password in cleartext. Dev mode is the no-auth path; production is
  encrypted.
