A broker compatible with Apache Kafka. The log stays in object storage.

Producers, consumers, and admin clients speak the Kafka wire protocol. The durable log lives in Cloudflare R2, or any S3-compatible bucket. A small set of Rust binaries replicates metadata, and a short write-ahead log, with Raft.

The same program, different node ids.

In the default durability mode a produce is acknowledged after a majority has the write-ahead log on disk. The object upload still happens. That slice of the log is then truncated.

What you point a client at is the bootstrap server. Compatibility is pinned to Apache Kafka 4.4.0, commit 1156b2752aaa28eafc0b4c4d387e63356793268d. Where a KIP and that tree disagree, the tree wins. kafka-clients, librdkafka through confluent-kafka, and franz-go produce, fetch, join groups, run transactions, compact a log, and call the admin APIs their libraries expose. A column in the compatibility doc stays unmarked until that client has really passed the call.

Roadmap

  1. Run Start one broker with Docker, or from a checkout. It listens for Kafka and forms a one-node group by itself.
  2. Bucket Give it a bucket before you care about the sealed log. Locally that is MinIO, until you point it at R2 or another S3 store.
  3. Clients Change the bootstrap address and keep the client you already have. kafka-clients, librdkafka, and franz-go have been run against the broker.
  4. Durability Choose when a produce is acknowledged. wal answers after a disk majority. r2 answers only after the object is stored.
  5. Production See what is still sharp, and when not to use Camus, before you trust it with a real workload.
